# PROMPT UNIFICADO: ARQUITECTURA ZIGBEE MESH CON NODOS VALIDADORES

Actúa como un **arquitecto senior de sistemas embebidos IoT** con más de 15 años de experiencia en redes Zigbee, seguridad en dispositivos de baja potencia, protocolos de malla IEEE 802.15.4 y desarrollo en C++ para entornos Linux embebido.

---

## CONTEXTO GENERAL

Se requiere diseñar una **plataforma profesional de red Zigbee Mesh** basada en Raspberry Pi (y otros sistemas compatibles) que funcione en Ubuntu, Debian, Raspberry Pi OS, macOS y Windows. El proyecto debe ser **multiplataforma, modular, escalable y exportable** para futuros proyectos IoT (smart home, smart city, agricultura, monitoreo industrial, etc.).

El diseño debe priorizar dos aspectos clave:

1. **Eficiencia energética**, especialmente para nodos finales con batería (End Devices).
2. **Seguridad robusta**, mediante la incorporación de **nodos validadores** que filtren y autentiquen mensajes antes de que consuman recursos en el resto de la red.

---

## OBJETIVO PRINCIPAL

Diseñar una arquitectura de red Zigbee Mesh que incluya:

- **Soporte completo para Zigbee PRO y Zigbee 3.0** (IEEE 802.15.4).
- **Roles de dispositivo**: Coordinator, Router, End Device y opcionalmente Gateway/Bridge.
- **Nodos validadores** (Validator Nodes) con capacidad de:
  - Validar integridad y autenticidad de mensajes (MAC, firmas ligeras, claves de sesión).
  - Filtrar mensajes duplicados, corruptos o malformados.
  - Delegar validación a routers padres para ahorrar energía en End Devices.
  - Mantener reputación de nodos y detectar ataques (replay, flooding, spoofing).
  - Actuar en modo pasivo (solo alertas) o activo (descartar/aislar).

## REQUISITOS FUNCIONALES DEL SISTEMA

### 1. Capas y módulos (Clean Architecture)

El sistema debe estructurarse en capas bien definidas:

- **Core**: gestión de hilos, eventos, estado global.
- **HAL (Hardware Abstraction Layer)**: abstracción para SPI/UART/GPIO.
- **Drivers**: controladores específicos para cada radio (MRF24J40, CC2530, CC2531, CC2652, EFR32, XBee).
- **MAC Layer**: IEEE 802.15.4 MAC, CSMA-CA, manejo de canales.
- **NWK Layer**: enrutamiento mesh, tablas de vecinos y rutas, descubrimiento de rutas.
- **APS Layer**: binding, grupos, gestión de endpoints.
- **ZDO Layer**: descubrimiento de dispositivos, comisionado, gestión de red.
- **Application Layer**: lógica de usuario, clusters ZCL personalizados.
- **Services Layer**: NetworkManager, MeshManager, SecurityManager, etc.
- **Storage Layer**: persistencia con SQLite (dispositivos, rutas, topología, claves).
- **CLI Layer**: interfaz de línea de comandos para administración.

### 2. Roles de los nodos

- **Coordinator**: Crea la red, asigna direcciones, actúa como Trust Center y puede ser validador principal.
- **Router**: Extiende la red, reenvía mensajes, mantiene rutas y puede actuar como validador secundario.
- **End Device**: Nodo final (puede ser sleepy), delega validación a su router padre.
- **Validator Node (dedicado opcional)**: Nodo que no participa en enrutamiento, solo monitorea y valida tráfico (similar a un IDS/IPS).

### 3. Nodos validadores (Validator Nodes)

**Ubicación estratégica:** Preferentemente routers con alimentación constante o el propio coordinador.

**Modos de operación:**
- **Pasivo**: Escuchan, validan y generan alertas sin interferir en el enrutamiento.
- **Activo**: Pueden descartar mensajes, notificar al emisor o reenviar solo los validados.

**Funcionalidades específicas:**
- Caché de validación (últimos N mensajes) para evitar reprocesar y detectar replay.
- Claves de validación derivadas (compartidas con Trust Center) para verificar autenticidad sin descifrar todo el payload.
- Sistema de reputación por nodo emisor (ratio de mensajes válidos/inválidos).
- Umbrales de fallos que provocan aislamiento y notificación al Trust Center.
- Registro de eventos de seguridad con sellado de tiempo y firma.

**Ahorro energético:**
- Delegación de validación a routers padres para End Devices sleepy.
- Validación por lotes (agrupar mensajes con misma clave temporal y validar en una operación).
- Reducción de retransmisiones al descartar tráfico inválido tempranamente.
- Políticas adaptativas según carga horaria (validación estricta en horas pico, ligera en horas valle).

**Seguridad:**
- Trust Center reforzado con asistencia de validadores para distribución de claves.
- Mecanismo de desafío-respuesta para nuevos nodos.
- Rotación periódica de claves de validación vía OTA.
- Detección de anomalías y reputación dinámica.

### 4. Flujo de validación típico

1. Emisor genera mensaje y lo firma con su clave de enlace (o clave de sesión compartida con validador).
2. El mensaje viaja por la malla hasta el primer nodo validador (generalmente el router receptor).
3. El validador:
   - Verifica firma.
   - Comprueba contador de secuencia (anti-replay).
   - Consulta caché para duplicados.
   - Evalúa reputación del emisor.
4. Si es válido, reenvía el mensaje (marcado como "validado") hacia el destino.
5. Si es inválido, descarta el mensaje, incrementa contador de fallos y, si supera umbral, inicia aislamiento.

### 5. Almacenamiento y persistencia

Usar SQLite para:
- Tabla de dispositivos (direcciones, tipo, clave, reputación).
- Tabla de rutas (destino, siguiente salto, costo, métricas).
- Tabla de vecinos (LQI, RSSI, última comunicación).
- Tabla de topología (relaciones padre-hijo).
- Tabla de eventos de seguridad (logs firmados).
- Tabla de claves (network key, link keys, claves de validación).

### 6. Servicios (managers)

- **NetworkManager**: creación/unión/salida de red, escaneo.
- **MeshManager**: gestión de malla, healing, reconfiguración.
- **RouteManager**: descubrimiento y mantenimiento de rutas.
- **SecurityManager**: gestión de claves, cifrado, autenticación.
- **DeviceManager**: registro, información, eliminación de dispositivos.
- **TopologyManager**: visión global de la red.
- **DiagnosticsManager**: health checks, heartbeats, estadísticas.
- **OTAUpdateManager**: actualizaciones de firmware seguras.

### 7. CLI (Command Line Interface)

Crear ejecutable `zigbee-cli` con comandos como:

- `network create|start|stop|join|leave|scan|status`
- `device list|info|remove|ping`
- `mesh topology|routes|neighbors|diagnostics`
- `security keys|rotate|show`
- `validator enable|disable|set-threshold|reputation`
- `ota update|status`

### 8. Logging y monitoreo

- Usar **spdlog** con niveles: TRACE, DEBUG, INFO, WARN, ERROR, FATAL.
- Registro estructurado (JSON) para integración con sistemas de análisis.
- Métricas clave:
  - Tasa de mensajes válidos vs. inválidos por emisor.
  - Latencia añadida por validación (objetivo < 10 ms).
  - Ahorro energético estimado en End Devices.
  - Número de alertas de seguridad y tiempo de respuesta ante ataques.

## REQUISITOS TÉCNICOS Y DE IMPLEMENTACIÓN (DISEÑO)

- **Lenguaje:** C++20 (uso de concepts, corrutinas, std::span, etc.).
- **Compilación:** CMake (mínimo 3.15) con soporte para Linux, macOS y Windows.
- **Dependencias oficiales:** Priorizar bibliotecas consolidadas como ZBOSS, zigbee-herdsman, Silicon Labs EmberZNet, Texas Instruments Z-Stack, o en su defecto implementar capas propias. Incluir también: Boost (asio, filesystem), OpenSSL, SQLite3, fmt, spdlog, GoogleTest.
- **Hardware:** Soporte para radios vía SPI o UART. Cada driver debe ser configurable en tiempo de compilación (opciones CMake).
- **Restricciones de recursos:**
  - RAM < 512 KB, flash < 2 MB para nodos embebidos (aunque en Raspberry Pi hay más, se debe diseñar para escalar a dispositivos más pequeños).
  - Algoritmos de validación ligeros (AES-128, SHA-256 solo cuando necesario).
  - Tablas de reputación y cachés eficientes (hash maps con expiración).
  - Sobrecarga de tráfico por validación < 10% adicional.
